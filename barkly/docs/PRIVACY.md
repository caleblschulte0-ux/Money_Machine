# Barkly — data flow

**What this document is.** An engineering description of what the software
does with data, written so that a privacy lawyer can reason about it without
reading the source. It is a factual account of behaviour.

**What this document is not.** A compliance claim. Nothing here establishes
that Barkly satisfies COPPA, the UK Age Appropriate Design Code, GDPR-K, or
any platform kids-category policy. Those are judgements for the publisher and
their counsel, and they depend on decisions that have not been made yet (see
[Open decisions](#open-decisions)). Implementing controls is evidence for that
argument; it is never the argument itself. A codebase that announces its own
compliance is a codebase nobody checked.

Current as of the commit containing this file. If the behaviour changes, this
changes in the same commit.

---

## 1. What the app collects

| Data | Where it comes from | Where it is stored | Leaves the device? |
|---|---|---|---|
| Microphone audio | Held TALK button only | Nowhere — never written to disk | **No** |
| Transcribed text | On-device speech recognition, or typing | In recent-turn memory (see §3) | Yes, to the dialogue service |
| Facts about the child | Extracted by the model from conversation | `AsyncStorage` on the device | Yes, as part of the prompt |
| Shared experiences | Generated by the app and the model | `AsyncStorage` | Yes, as part of the prompt |
| Install identifier | Randomly generated on first launch | `AsyncStorage` | Yes, as a request header |
| Barkly's stats / character | Derived from interaction | `AsyncStorage` | Summarised into the prompt |

Nothing else. There is no advertising SDK, no analytics SDK, no crash
reporter, no attribution framework, and no contacts/location/photo access.

## 2. The microphone

Capture runs only between the press and release of the TALK control
(`providers/stt/expoSpeechRecognitionStt.ts`; the `SpeechToTextProvider`
contract states this as a requirement, not a convention). There is no wake
word and no background listening; the app requests no background audio mode
(`shouldPlayInBackground: false`).

Recognition is performed by the operating system's own speech recognition.
The audio buffer is not persisted by this app and is not transmitted by it.
**Note for counsel:** on iOS, the platform's speech recognition may itself
send audio to Apple depending on device and locale settings. That is Apple's
processing under their terms, outside this app's control, and it should be
disclosed as such rather than described as "on-device" without qualification.

The microphone permission is requested during onboarding, at the moment
Barkly asks to hear the child, and never at launch. Declining leaves a fully
working app that takes typed input.

While listening, the character visibly changes pose and the UI shows a
listening state. Microphone activity is never invisible.

## 3. What is sent to the dialogue service

One request per utterance, containing:

- the system prompt: Barkly's personality, his current stats, where he is,
  and the fenced memory block (§4)
- the recent conversation turns (a bounded window, not the whole history)
- the newest utterance

and the headers `x-barkly-device` (the random install identifier) and
`x-barkly-app-token` (a shared build token, not a user credential).

Requests go to the Barkly proxy (`barkly/server/`), which holds the vendor
credential and forwards to Anthropic. The proxy **rebuilds** the request body
from recognised fields, so a modified client cannot add fields.

**Proxy logging is content-free by construction.** The logger takes an event
name plus a flat record; numbers and booleans pass, and a string is written
only if its field name is on an explicit allowlist. Message text has no such
field. The install identifier is SHA-256 hashed before it is written, so logs
are not a list of who talked to Barkly. See `server/lib/logging.mjs`.

The proxy records token counts and, if the operator configures voice, character
counts. It does not record what was said.

**Vendor retention is not ours to state.** What Anthropic (and, if enabled,
ElevenLabs) retains, and for how long, is governed by the publisher's
commercial agreement with each vendor. That agreement — including whether a
zero-retention or no-training term applies — is a decision for the publisher
and must be reflected in the published policy. This app cannot make that
representation on their behalf.

## 4. What is stored on the device, and how it is bounded

Three tiers (`barkly/memory.ts`):

1. **Recent turns**, verbatim, a bounded window.
2. **A consolidated digest** of everything older, which is a summary rather
   than a transcript. Older verbatim turns are dropped, not archived.
3. **Facts and experiences**, structured and scored, ranked by
   importance × confidence × recency so the prompt stays a bounded size no
   matter how long the app is used.

All of it is in this app's `AsyncStorage` sandbox on this device. It is not
synced to a server, not backed up to the publisher, and not readable by other
apps. Whether it is included in the user's own iCloud/Android device backup
depends on their OS backup settings; the app does not opt out of that today
and that is a decision listed below.

**Prompt-injection containment.** Everything derived from a user or a previous
model reply is sanitized (`barkly/facts.ts`) and enclosed in a delimited block
that the system prompt frames as untrusted reference data. This matters for
privacy as well as safety: it is what stops stored text being able to
re-instruct the model about what to do with other stored text.

## 5. Deletion

"Forget everything", behind a parental gate, deletes all facts, experiences,
turns, the digest, the stash, the character drift, and the install identifier,
and returns the app to first-launch state including the introduction. It is
immediate and irreversible.

Individual facts can be deleted one at a time from Settings, which lists
**everything** he knows — not a summary of it.

Deletion is local. Anything already sent to a vendor is subject to that
vendor's retention terms (see §3).

## 6. Parental gate

A two-digit arithmetic challenge with freshly generated numbers guards
permanent deletion and any navigation out of the app to the web
(`ui/ParentalGate.tsx`). It is a speed bump sized to stop a young child acting
accidentally, and the code says so; it is not age verification and must not be
described as such.

## 7. Open decisions

These are product and legal calls, not engineering gaps. Each one changes what
the published policy has to say.

1. **Kids Category or general audience?** This determines whether third-party
   analytics are permissible at all, what the age gate must look like, and
   whether the dialogue vendor's terms are usable in that context.
2. **Vendor terms.** Retention and training terms with Anthropic (and
   ElevenLabs, if voice ships) must be settled and then reflected here.
3. **Device backup.** Whether Barkly's memory should be excluded from
   iCloud/Android backup.
4. **Published policy URL.** `ui/PrivacySheet.tsx` currently links a
   placeholder and says so on screen. It must be replaced before submission.
5. **Retention window.** The app currently keeps memory until deleted. Whether
   an automatic expiry is wanted is a policy choice, not a technical one.
6. **Support and requests.** No channel exists yet for a parent to ask what is
   held or to request deletion by any route other than the in-app control.
